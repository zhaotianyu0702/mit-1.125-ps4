What Coding-Agent Results Actually Measure

As of: 2026-10-12

A model bill can fall. A benchmark can improve. An agent can complete thousands of runs. Each may be a real measurement, yet none alone answers the question a small team cares about: did the team deliver better software with less total effort? Recent reports measure different links in that chain. The reported task and cost improvements give reason for optimism. The next step is to establish which gains carry through to accepted software changes, including review and repair. (Sources: Asana browser-agent study) (Sources: LegalOn cost account) (Sources: Flywire run count, 15:44; online-evaluation status, 15:07) (Sources: Asana study; LegalOn account; GitHub ReviewBench; Flywire presentation)

A completed task is a bounded result

Asana reports a 144-run browser-agent study comparing four models and variations in history, caching, and screenshot handling. Each configuration gathered six fields for each of 32 books from a public demo catalog. The company says its optimized GPT-6.1 Sol workflow averaged about four minutes and $0.47 in estimated model cost, and that all 18 runs using the larger history budget returned correct answers. This is useful evidence about task completion, runtime, and estimated cost under those conditions. It is not evidence about a coding agent’s productivity. (Sources: Asana browser-agent study)

Software work adds steps that the browser task does not measure: whether a patch is correct in its repository, whether it introduces a regression, how long review and repair take, and whether the final change is worth shipping. Asana’s result cannot answer those questions. The publisher presents the study as a customer benefit, so its reported results should be attributed to the company and kept within the tested task. (Sources: Asana browser-agent study)

Lower cost creates an opportunity to measure value

LegalOn’s account says model selection, feature restrictions, and budgets tailored to business areas reduced estimated daily AI costs by about 65%, while development speed was maintained. The same account says the company is still building a pipeline to connect customer value with the AI cost invested in each feature release. The distinction is important: an estimated usage reduction is a cost measure; the release-value measure is still in development. (Sources: LegalOn cost account)

A lower bill can help a team manage spending. On its own, it does not show whether customer outcomes improved, whether engineers spent less time, or whether review work offset the savings. LegalOn’s figures are a company-reported case study, not an independent estimate for other teams. Its own description of a metric still being built makes clear what the cost figure cannot settle. (Sources: LegalOn cost account)

Benchmarks and run counts answer different questions

GitHub’s ReviewBench is more directly about code review. The company describes a versioned dataset, judge, and matcher, and reports that offline changes evaluated before A/B tests consistently pointed in the same direction as later production results in its experiments. A versioned benchmark can make comparisons easier to inspect and repeat, and GitHub’s reported alignment may help decide which changes deserve a production test. But this is the publisher’s account of its own validation; the supplied evidence does not include independent replication. ReviewBench also measures review behavior, not end-to-end delivery for a small team. (Sources: GitHub ReviewBench report)

Flywire’s presentation supplies a useful counterexample to treating usage as quality. Its presenters report more than 9,700 automated code-review runs in 30 days and say online evaluations are not yet available. A run count tells us that the workflow was used. It does not reveal whether reviews found consequential problems or reduced human effort. The presenters also describe container limits that can prevent some agents from running native builds or unit tests. That operational context matters when interpreting the number, but still does not provide an outcome measure. (Sources: Flywire run count, 15:44; online-evaluation status, 15:07) (Sources: Asana study; LegalOn account; GitHub ReviewBench; Flywire presentation)

These reports cannot be combined into one productivity estimate. Asana reports one browser task’s completion, time, and model cost; LegalOn reports estimated cost reduction while a release-value metric is in development; GitHub describes a code-review benchmark and its own offline-to-production alignment; Flywire reports volume while online evaluation remains pending. Their tasks, systems, and scale differ, and the accounts are primarily from vendors or platforms. More detail makes a claim inspectable, but does not make it independent or transferable. (Sources: Asana study; LegalOn account; GitHub ReviewBench; Flywire presentation)

A small team can close part of this gap with a bounded comparison. Select representative repository tasks, define acceptance criteria in advance, and compare assisted work with the usual process. Independently inspect the artifact, count failures and rework, record reviewer time and total elapsed time, and include costs. Repeat across similar tasks so one unusually easy or difficult run does not decide the result. This is a proposed method derived from the reports’ limits, not a finding already established by them. (Sources: Asana study; LegalOn account; GitHub ReviewBench; Flywire presentation)

I take a positive view of the opportunity for efficiency gains: the reported task improvements and cost reductions make active experimentation worthwhile. A common productivity percentage would overstate this evidence, but waiting for a universal result would miss the chance to learn from a well-measured local trial.

The question for the next edition is concrete: where does the opportunity become a verified gain once quality, review effort, failures, and total cost are counted?
