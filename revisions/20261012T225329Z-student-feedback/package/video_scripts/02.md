# What Coding-Agent Results Actually Measure

**As of: 2026-10-12**  
**Companion video script | Approx. 3–5 minutes**

## Narration

When an agent gets cheaper, completes more runs, or earns a better benchmark score, what have we learned? Each number measures something useful, and the reported improvements give reason for optimism. To find the gains that matter to a small team, follow the work through to accepted software and include review and repair.

Asana reports a 144-run browser study comparing four models and workflow settings. [02-c1] Every configuration collected six fields for each of 32 books from a public demo catalog. The company says its optimized GPT-6.1 Sol workflow averaged about four minutes and 47 cents in estimated model cost. All 18 runs with the larger history budget returned correct answers. This is evidence about one task’s completion, runtime, and estimated cost. It is not a coding productivity result.

Software delivery adds questions that task does not answer. Was the patch correct in the repository? Did it introduce a regression? How much time did review and repair take? Those are outcomes a coding trial must measure directly. Asana’s publisher-reported results stay within the tested browser workflow. [02-c1]

LegalOn’s account measures another part of the picture. [02-c2] The company reports that model selection, feature restrictions, and budgets reduced estimated daily AI costs by about 65%, while development speed was maintained. But LegalOn also says it is still building a pipeline to connect the cost of each feature release with customer value. So the cost reduction is a reported operational measure; the customer-value measure is not yet a result.

A lower bill can help with budgeting. It does not, by itself, show that the work was more valuable or that engineers spent less time. Those need their own measures.

GitHub’s ReviewBench is closer to code review. [02-c3] The company describes a versioned benchmark and reports that offline changes tested before A/B experiments consistently pointed in the same direction as later production results. That may help decide which changes deserve a production test. The evidence here is GitHub’s account of its own experiments, without independent replication. A code-review benchmark also cannot stand in for end-to-end delivery.

Flywire’s presenters report more than 9,700 automated review runs in 30 days, while also saying online evaluation is not yet available. [02-c4] Run volume shows usage, not quality or time saved. They describe container limits that can prevent some agents from running native builds or unit tests. That context helps interpret the system’s operating conditions; it does not supply a quality measure. [02-c5]

These figures answer different questions. A browser task’s cost and completion, a company’s estimated AI spending, a code-review benchmark, and a run count do not add up to one productivity estimate. The accounts also differ in scale and come chiefly from vendors or platforms. Detail makes a claim easier to inspect, not automatically independent or transferable. [02-c5]

For a small team, compare representative tasks against the usual process. Define acceptance criteria in advance, check the artifact independently, and record failures, rework, review time, total time, and cost. Repeat across similar tasks. That is a way to investigate the gap in the evidence, not a result already proved by these reports.

I am positive about the opportunity for efficiency gains. These reports make active experimentation worthwhile, while leaving the size of any coding-team gain uncertain. Which recurring repository task will you try first, and does its advantage remain after quality checks, review, and rework?
