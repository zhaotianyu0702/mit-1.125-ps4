# Coding agents move into the delivery system

**As of: 2026-10-12**  
**Companion video script | Approx. 3–5 minutes**

## Narration

When an AI assistant starts working inside a repository, the question is bigger than whether it can write code. What project context does it receive? What can it change? And how can the team tell whether the whole workflow helped?

Recent accounts point toward designing agents as part of delivery: with instructions, permissions, review paths, and records of what happened. These implementation examples offer plausible ways to improve efficiency. I favor trying them and checking whether the gains survive setup, review, and rework.

[01-c1] GitHub describes four ways to tailor Copilot to a project: repository or path instructions, reusable skills, specialized agents, and connections to tools and data through MCP. The goal is to bring conventions and repeatable procedures close to the code. That describes product capabilities; it is not proof they improve results.

Flywire’s presenters describe a more bounded review workflow. [01-c2] Deterministic steps gather merge request information and classify risk. The review agent can read code but cannot edit files or push changes. Findings return to the merge request for human review. This is Flywire’s account of its own implementation. It shows one way to define an agent’s role, not a measured improvement in review quality.

Together, those accounts suggest a shift in what a team configures. Context and reusable procedures sit alongside permissions and handoffs. A small team may need to maintain those pieces as part of its delivery process. That is an interpretation of the examples, not a result they tested. [01-c5]

Infrastructure matters too. [01-c3] GitHub says it is rebuilding Git infrastructure for developers and agents working at the same time, and reports up to 35 times higher write throughput in internal benchmarks. The supplied passages do not specify conditions well enough to predict what a typical team would see.

Asana’s browser study offers a measurement example from another kind of task. [01-c4] In 144 vendor-reported runs, the workflow collected six fields for each of 32 books from a public demo catalog. Asana says its optimized GPT-6.1 Sol setup averaged about four minutes and 47 cents in estimated model cost. All 18 runs with the larger history budget returned the correct answer. Those results describe that extraction task, not coding productivity. Its headline cost comparison also changes both model and workflow, so it cannot isolate either one.

Across these accounts, context, bounded permissions, and observable runs appear as parts of the workflow. That connection is useful for designing a trial, but it does not prove that the practices improve small-team coding outcomes. [01-c5]

A practical test starts with one recurring task. Define the expected result before the agent runs. Save the configuration, inspect the patch, and record failures, review time, corrections, elapsed time, and cost. Compare against the team’s usual process on similar work. This is a proposed checklist, not a validated standard.

My conclusion is positive about the opportunity. Better context, repeatable procedures, and bounded review give teams useful places to start. The sources do not establish a typical small-team productivity gain, so measure total effort and quality on your own tasks. Keep and expand the uses that work.
