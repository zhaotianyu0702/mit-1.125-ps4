# Coding agents move into the delivery system

As of: 2026-10-12

A coding agent is easy to evaluate in a demo: give it a task and see whether it produces code. In a real team, the harder question is how that code moves through the delivery process. What project knowledge does the agent receive? Which actions can it take? Where does a person inspect the result? Recent accounts from GitHub, Flywire, and Asana describe different pieces of that system. These accounts give small teams concrete ways to pursue efficiency gains: better context, repeatable procedures, and bounded review. I favor trying those ideas while measuring whether the gains survive review and rework.

GitHub’s Copilot guide describes four ways to make an agent more specific to a project: repository or path instructions, reusable skills, specialized agents, and connections to tools and data through MCP. The practical idea is to keep conventions and recurring procedures close to the code, so the team need not rebuild that context in every prompt. These are vendor-described capabilities. Their presence does not establish that a team’s output improves. [01-c1]

Flywire’s presenters describe a different layer: controlling the path a review takes. In their account, deterministic code gathers merge request information and classifies risk; the review agent can inspect code but cannot edit files or push changes; findings return to a merge request for people to review. That architecture gives the agent a defined role inside an existing approval process. It is a company description of its own implementation, not comparative evidence that the controls catch more defects or save time. [01-c2]

Together, the examples shift the design question from “Which model should we use?” to “What workflow should surround it?” One account emphasizes context and reusable procedures; the other emphasizes permissions and handoffs. A small team adopting an agent may therefore take on maintenance work: keeping instructions current, deciding what tools are available, and making sure a human can evaluate changes. That is an inference from the two implementation accounts, not a measured estimate of the effort or return. [01-c5]

The delivery system also includes the infrastructure agents depend on. GitHub says it is rebuilding Git infrastructure for concurrent developer and agent workloads, and reports up to 35 times higher write throughput in internal benchmarks. The stated pressure comes from GitHub’s busiest repositories and service architecture. The supplied passages do not provide benchmark conditions that would predict performance in a typical small-team repository, so the figure should be read as a vendor-reported internal result, not a forecast. [01-c3]

Asana’s browser-agent study illustrates a separate design need: observe the run as well as the final answer. Its vendor-reported study covered 144 runs of a task that collected six fields for each of 32 books in a public demo catalog. Asana reports that its optimized GPT-6.1 Sol workflow averaged about four minutes and $0.47 in estimated model cost; all 18 runs with the larger history budget returned the correct answer. The report also discusses a 76-fold cost comparison, but that comparison changes both model and workflow. It cannot isolate the effect of either change. More importantly, this was information extraction in a browser, not coding productivity. [01-c4]

For a small team, these examples make a focused trial worth undertaking. Choose one recurring coding task and write down what a correct result means before an agent runs. Save the instructions and tool configuration, inspect the resulting patch, and record failures, correction rounds, review time, elapsed time, and cost. Compare like tasks with the team’s usual process. This checklist is our synthesis of the sources; it is not a validated standard, and the sources do not show that these steps will produce a net delivery gain. [01-c5]

The evidence is complementary but incomplete. GitHub and Flywire describe implementations, Asana reports a bounded browser task, and the sources differ in scale and purpose. None supplies an independent comparison of coding-agent workflows in small teams. My conclusion is cautiously positive: better context, bounded permissions, and visible run records offer plausible routes to more efficient delivery. Small teams should explore those opportunities and expand the uses that save total effort while preserving quality. The sources do not establish a typical gain or guarantee one for every task.

For the next edition: on a representative coding task, does the workflow save time after setup, review, and rework are included?
