Let's take a deeper look at the technical architecture
of orbit.
Originally, we began with a simple container setup
on AWS ECS Fargate, where the orchestration layer

lived inside the same container.
As our needs grew, we both were separating
the orchestration layer, the agent runtime environment,
and the session state into distinct components.
This improves isolation, maintainability,
and resource allocation.
It also makes the system more resilient,
because an error in the effort does not kill the sandbox.
And it lets us scale each piece independently
and adapt to changing requirements.
Fargate lets us scale tasks elastically,
so we can run a very large number of agents in parallel.
It was also really easy to deploy orbit,
because we already had Victoria, our path
that scales applications without any effort.
But that scale needs car rails, so the platform
is not misused.
First, timeouts.
Every agent stops after a configurable amount of time.
Second, rail limits, which are aggressive by default.
A broken API integration could start
spawning thousands of agents and make our build much bigger.
The limits keep that under control.
Third, concurrency control.
Our control plane uses logs to prevent duplicate executions
of the same task.
For example, if our code review is already running,
we drop the duplicator request.
Running agent is a Victoria, comes with container limits.
Victoria uses standard Fargate task definitions,

Our baseline agent container includes

Another crucial pattern we rely on
is isolated component evaluation.
Evaluating complex end-to-end agent workflows
in synthetic benchmark environments
is often noisy, expensive, and difficult to reproduce
consistently.
Instead of trying to evaluate entire workflows
from start to finish, our evaluation harness
isolates individual LLM steps.
By injecting exact historical state and context directly
into specific workflow nodes, we can evaluate model output
quality, measure from adjustments,
and cut performance regressions quickly and cost effectively.
So how do we know that an agent is good enough?

We then extract traces from real executions

For now, each golden data set is version in the repo story,

Based on those results, we improve the prompt or chance
the model, and we run the data set again to compare.
We do not have online evaluations yet,

Our goal is to run the whole evaluation loop inside orbit

First, you deploy your agent.
