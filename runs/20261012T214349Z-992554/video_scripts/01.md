# Coding agents move into the delivery system

**As of: 2026-10-12**  
**Estimated narration:** about 4 minutes

## Narration

When a coding assistant moves from answering a prompt to taking part in repository work, the question changes. It’s no longer only, “Can it write code?” It’s also: what context does it get, what can it change, and how can a team tell whether the workflow helped?

The material here points to a shift from standalone code generation toward agents built into repository workflows, review, and infrastructure. That makes context, evaluation, governance, and capacity part of delivery design. The evidence describes implementations and bounded experiments. It does not establish that small teams ship more or better code.

[01-c1] GitHub describes four ways to configure Copilot around a project: repository or path-specific instructions, reusable skills, specialized agents, and tools connected through MCP. The idea is to give an assistant project conventions and repeatable procedures, or connect it to relevant tools. That is a description of available capabilities, not evidence they improve outcomes.

[01-c2] Flywire’s presenters describe a more tightly structured enterprise workflow. Predictable steps are handled in code. A review agent can read code, but cannot modify it; its findings return through a merge request, where people review and approve changes. This is a company’s account of its own implementation, but it gives a concrete example of putting an agent inside familiar engineering controls.

Together, these accounts suggest a practical design principle: make context explicit, bound what the agent can do, and keep its work reviewable. That’s an inference from the sources, not a measured result for small teams.

The infrastructure story adds another piece. [01-c3] GitHub says it is rebuilding Git infrastructure to handle developers and agents working concurrently, and reports up to 35 times higher write throughput in internal benchmarks. The supplied material does not explain the benchmark conditions enough to predict what an ordinary team repository would experience.

And what about measurement? [01-c4] In a vendor-reported study, Asana ran 144 browser-agent trials on a task: collect six fields for each of 32 books from a public demo catalog. Its optimized GPT-6.1 Sol workflow averaged about four minutes and an estimated 47 cents in model cost per run. All 18 runs with the larger history budget returned the correct answer. That’s useful evidence about the tested workflow and task. It is not a coding-productivity result.

[01-c5] Across these examples, a common thread emerges: agent delivery depends on context, bounded permissions, and observable runs. GitHub describes ways to supply project context; Flywire describes permission limits and human review; and Asana connects a task-specific result to configuration changes and recorded sessions. The connection is suggestive, not proof that these practices improve small-team coding outcomes.

So what evidence would justify trusting an assistant with more of a small team’s delivery workflow? Start with a recurring task. Record the baseline, define what a correct result looks like, and track review effort, failures, runtime, and cost across repeated runs. Keep changes reviewable. Then compare the same task under the same conditions.

The limitation is simple: these sources don’t provide that independent, comparable small-team coding study. Until they do, treat workflow features and impressive task-specific results as reasons to measure—not as proof of better delivery.
