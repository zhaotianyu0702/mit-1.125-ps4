# Coding agents move into the delivery system

For a small team, adding an AI coding assistant can look like a tooling decision: choose a model, connect it to a repository, and ask it to make a change. Recent accounts from GitHub, Flywire, and Asana point to a broader shift. The work is increasingly about fitting agents into the delivery system: supplying project context, defining which actions are allowed, and recording enough evidence to judge whether a run worked. That changes what a team must evaluate. A convincing demo of code generation is not yet evidence that a team ships better software.

GitHub’s beginner guide describes four ways to tailor Copilot to a project: repository or path-specific instructions, reusable skills, specialized agents, and MCP connections to tools and data. These features place conventions and repeatable procedures near the codebase, rather than requiring engineers to restate them for each task. This is a vendor’s description of workflow capabilities, not proof they improve results. [01-c1]

Flywire’s presenters describe a related pattern at a much larger, regulated company. Their review workflow uses deterministic steps to gather merge request information and classify risk before a model reviews code. They say the review agent cannot edit files or push changes, and that its findings return to a merge request for human review. This is Flywire’s account of its own implementation; it shows how a team can put boundaries around an agent, not how much those boundaries improve code quality. [01-c2]

The connection between these examples is a shift in the unit of design. Instead of treating an agent as a free-form assistant, both accounts describe a workflow whose context, tools, permissions, and handoffs are deliberately configured. GitHub emphasizes repository knowledge and reusable procedures; Flywire emphasizes bounded access and review through existing engineering processes. For a small team, the practical implication is that adopting an agent may mean maintaining instructions, skills, permissions, and review paths, alongside the code itself. This is an interpretation of the two implementation accounts, not evidence that the added work pays off. [01-c5]

Infrastructure becomes part of that question as agents run concurrently. GitHub says it is rebuilding Git infrastructure to support simultaneous developer and agent work, and reports up to 35 times higher write throughput in internal benchmarks. The post describes pressure from GitHub’s busiest repositories and its own service architecture. It does not provide benchmark conditions in the supplied passages that would predict how an ordinary small-team repository performs. The figure is a vendor-reported internal result, not a general performance estimate. [01-c3]

Asana’s browser-agent study adds a useful measurement example, with a different task and important limits. In a vendor-reported study of 144 runs, the workflows gathered six fields for each of 32 books from a public demo catalog. Asana reports that its optimized GPT-6.1 Sol setup averaged about four minutes and $0.47 in estimated model cost, and that all 18 runs with the larger history budget returned the correct answer. Those results concern a specific extraction task. The prominent 76x cost comparison also changes both model and workflow, so it cannot isolate the effect of either change, much less establish coding productivity. [01-c4]

What the Asana example contributes is a reminder to record the run, the configuration, the task outcome, and the cost together. GitHub’s guide shows where project context can be specified; Flywire’s account shows how actions and handoffs can be bounded; Asana describes recording requests, traces, and results while comparing workflow configurations. Taken together, these accounts suggest a practical evaluation checklist for a small team: define a repeatable coding task, record the instructions and tools used, track edits and review findings, and compare task completion and review effort across runs. That checklist is our synthesis, not a validated standard or proof that these controls produce better delivery. [01-c5]

The evidence remains limited. GitHub and Flywire describe implementations rather than controlled small-team comparisons. Asana’s catalog task is not a coding task, and Flywire’s enterprise constraints and infrastructure differ from those of a small team. The supplied material therefore supports a change in how teams are structuring and measuring agent workflows; it does not show that small teams ship more or better code as a result. Comparable, independent coding studies could change that conclusion.

For the next edition: in a small-team coding trial, do these workflows reduce total delivery time after human review, rework, and agent setup are counted?
