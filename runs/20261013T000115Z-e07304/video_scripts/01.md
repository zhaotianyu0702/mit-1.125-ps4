# Coding agents are entering the delivery workflow; the gains still need checking

**As of: 2026-10-13**  
**Estimated spoken length: about 550 words (3–5 minutes)**

## Narration

A coding agent can now be guided by a project’s own rules, given browser access, and placed inside a defined review process. That changes where a small team can try one. The decision is whether to expand those uses—and what evidence would justify doing so.

GitHub’s tutorial describes four ways to tailor Copilot to a codebase: repository and file-specific instructions, repeatable skills, specialized agents, and connections to tools such as Playwright. Its examples show how a team can provide conventions and let an agent interact with an interface. That is practical setup guidance; the supplied material does not establish that these options are new or that they improve delivery outcomes. [01-c1]

A practitioner account shows a different part of the workflow. Simon Willison describes building a Django newsletter feature using voice while cooking, then checking a visual preview and reviewing a pull request. He says the voice session lasted about half an hour. During review, he changed the agent’s choice to use a Git subprocess for an import, and spent another half hour prompting by keyboard before deploying. The account illustrates how voice, preview, and detailed review can fit together on one feature. It is one person’s experience, not a controlled comparison of productivity. [01-c2]

Now compare that hands-on example with Flywire’s account of its internal workflows. In a machine-transcribed video, Flywire describes combining deterministic steps with model calls. For code review, it says the model can read and search code but cannot edit files or push changes; people still review and approve merge requests. That is an example of putting limits and familiar review points around an agent. The transcript has not been audio-verified, and these implementation details do not independently establish outcomes. [01-c4]

Together, these examples point to a useful way to experiment: place an agent in a specific step, supply the context or tools it needs, and keep a clear review path. GitHub offers setup patterns; Willison’s account shows a person switching between interaction modes and reviewing a change; Flywire describes restricted access within a workflow. That combination makes bounded trials more practical. It does not show that a team will save time overall or preserve quality. [01-c5]

Asana provides a concrete measure, with a narrow scope. It reports that an optimized browser workflow averaged about four minutes and 47 cents in estimated model costs per run, compared with its original production setup on Model B. The task was fixed: collect six fields for each of 32 books from a public demo catalog. Those results concern that task and estimated model costs; they do not establish lower total delivery cost or general coding productivity. [01-c3]

For a small team, the next step is a bounded trial on a repeated task. Record the work’s starting quality, model and tool costs, elapsed time, human review and correction effort, and the final result. Compare with the team’s usual process under similar conditions. Expand the agent’s role when those measurements show quality is preserved and total effort falls. That is an editorial recommendation, not a measured gain from these sources.

The evidence here comes from vendor guidance and reports, one practitioner’s project, and a machine-transcribed vendor video. It does not provide a controlled comparison of end-to-end delivery by small teams. The opportunity is real enough to test; the size and reliability of any gain remain questions for a team’s own evidence.
