# A small trial should measure the work around the agent

**As of: 2026-10-13**

## Narration

Your coding agent finishes a task, the checks turn green, and it reports success. Should it get a bigger role on the next change? The useful question is what the team received—and what it took people to deliver it.

For a small team, I recommend an active, bounded experiment: pick one recurring workflow, measure it carefully, and expand its use when verified quality holds and total team effort falls. That is an editorial recommendation, not a measured productivity result from these sources.

Start with a task that repeats and has a clear acceptance check. Record how the team handles it now. Keep the task, agent configuration, and evaluation setup versioned so you can compare runs fairly. GitHub describes versioning its ReviewBench dataset, judge, and matcher to make evaluations comparable under the same configuration. Stack Overflow’s production field guide recommends comparing each release with a baseline, not just a pass-or-fail floor. Together, these practices suggest treating the trial like a repeatable experiment. [03-c1]

Next, inspect the delivered artifact independently. Did it meet the task’s acceptance criteria? Did automated checks pass? What did a person correct, override, or send back for rework? Stack Overflow warns that verification should not share a failure mode with the work itself. A green status can tell you a process ended; by itself, it cannot establish that the intended change is there. [03-c2]

Then count the work around the agent. Include setup, waiting, review, fixes, and deployment in both human effort and elapsed time. In one account, developer Simon Willison describes spending about half an hour on voice-driven development, then another half hour typing prompts and reviewing changes before he was ready to deploy. That is a useful reminder about what to count, but it is one person’s experience, not a comparison showing an efficiency gain. [03-c3]

The cross-source insight is that the trial needs two ledgers: one for whether the artifact is right, and one for the full effort and cost of getting it delivered. An impressive benchmark or a fast run cannot stand in for both. For example, Asana reports 144 runs on one fixed browser task: collecting six fields for each of 32 books from a public demo catalog. Its optimized GPT-6.1 Sol workflow averaged about four minutes and 47 cents in estimated model costs per run. Those figures describe that task and model spend; they do not establish total delivery cost or expected savings for another team. [03-c4]

Track tool and model costs per task and per delivered change. Set a spending limit and decide what happens when it is reached. LegalOn describes routing different tasks to different models and setting usage limits; its feature-level customer-value metric was still being built. Simon Willison argues for hard budget caps to contain runaway charges. These accounts motivate tracking cost and interruption risk; they do not validate one cost policy or promise savings. [03-c5]

Before allowing unattended or parallel runs, check whether state can be recovered, tool permissions are scoped, failures are isolated, and runs stop at a time limit. A sampled podcast interview discusses saving state beyond ephemeral runs and controlling tool access through a gateway. Flywire describes time limits, restricted container environments, read-only code review, and evaluations that isolate individual model steps. Flywire also says online evaluations were not yet in place. These are implementation ideas to test, not proof that either design works for a small team. [03-c6]

So run the experiment, and let evidence earn each expansion. Continue when quality holds and measured total effort falls; narrow or stop if rework, access failures, or costs exceed your limits. The supplied evidence does not establish that a bounded trial will improve productivity, and no single metric is enough. Your own repeated results are what can justify giving an agent more of the workflow.

## Visual direction

- Open on a pull request with a green check and a “Task complete” message. Hold, then reveal the unreviewed diff beneath it.
- Show a simple trial card: **Recurring task → baseline → fixed evaluation → bounded run**. Keep the same task and configuration visible across comparisons.
- For artifact verification, show acceptance criteria beside the diff, then mark corrections, overrides, and rework. Do not equate a green check with completed work.
- Animate a timeline labeled **setup, waiting, review, fixes, deployment**. Attribute Willison’s example on screen as one personal account.
- Show two side-by-side ledgers: **Artifact quality** and **Full delivery effort and cost**. In the Asana example, label the task and the figures as reported, with model cost distinguished from total delivery cost.
- End on a bounded expansion dial with quality, team effort, cost, and safety checks. Use neutral narration; if an AI-generated presenter or voice is used, treat it as a production instruction until rendered.
