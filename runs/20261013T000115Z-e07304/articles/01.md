# Coding agents are entering the delivery workflow; the gains still need checking

**As of: 2026-10-13**

A coding agent can now be given a repository’s conventions, asked to follow a repeatable check, connected to a browser, and placed inside a defined workflow. For a small team, that changes the practical question from whether to try an agent to which delivery step is worth a measured trial. The supplied accounts make experimentation more actionable, but they do not establish that agents generally make software delivery faster or cheaper. [01-c1] [01-c5]

[GitHub’s Copilot tutorial](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-how-to-teach-copilot-about-your-codebase/) describes repository and path-specific instructions, reusable skills, specialized agents, and MCP connections such as Playwright. These give a team ways to encode context and procedures it would otherwise repeat, and to ask an agent to interact with an interface. GitHub presents these as configuration guidance; the supplied material does not show when each capability first appeared or measure an effect on delivery. [01-c1]

A practitioner’s account shows why these workflow pieces matter together. Simon Willison describes building a Django newsletter feature by voice while cooking, checking the work in a visual preview, then reviewing a pull request and changing an import approach. He reports about half an hour of voice interaction and another half hour of keyboard prompting before he was ready to deploy. The example suggests voice can help shape a feature while visual feedback and conventional review carry the work into detail. It is one developer’s account, not a comparison showing less total effort. [01-c2] [01-c5]

The same distinction applies to cost and runtime figures. Asana reports that an optimized browser workflow averaged $0.47 in estimated model costs and about four minutes per run, compared with its original production setup on Model B. The task was collecting six fields for each of 32 books from a public demo catalog. Asana frames the work as a way to offer customers faster, more capable models at sustainable operating cost, so its figures are a vendor’s reported result with a commercial interest in the outcome. They measure a bounded browser task and estimated model costs, not engineering time, review burden, total delivery cost, or general coding productivity. [01-c3]

Flywire’s video offers a complementary account of how an organization can constrain agent work. In the machine transcript, speakers describe placing model calls between deterministic steps, restricting a code-review agent to reading and searching, and retaining human merge-request review and approval. This connects workflow expansion to review controls: a team can let an agent participate in more steps while keeping changes subject to familiar checks. But Flywire is describing its own platform and practices, not independently demonstrating their effect on outcomes; the transcript has not been audio-verified. [01-c4] [01-c5]

Taken together, the sources point to a useful trial design, not a proven productivity result. Start with one repeated, bounded task. Record its baseline and agent-assisted total effort, including setup, corrections, review, and follow-up. Track task quality against the team’s existing checks and acceptance criteria, alongside model cost and runtime. Keep a human responsible for reviewing consequential changes. Then expand the agent’s role only when the team’s own evidence shows that quality holds and total effort falls. That is an editorial recommendation grounded in the workflow examples; the sources have not measured those gains for a small team. [01-c5]

This evidence is limited in ways that matter: it combines vendor accounts, one practitioner’s experience, and a machine-transcribed vendor video, without a controlled, end-to-end comparison among small teams. Asana’s result concerns one fixed catalog task, while Willison’s account cannot isolate time saved from time shifted between voice, preview, and keyboard review. These examples justify active, bounded experimentation and careful expansion, while leaving the size and consistency of any delivery gain to be established locally. [01-c2] [01-c3] [01-c4] [01-c5]

**Question for the next edition:** In a condition-matched small-team trial, does assigning an agent a defined delivery step reduce total human effort while maintaining the team’s usual quality standard?
