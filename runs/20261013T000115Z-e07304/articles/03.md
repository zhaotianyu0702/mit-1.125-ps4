# A small trial should measure the work around the agent

**As of: 2026-10-13**

A coding agent can finish a task quickly and still leave a team with more work than it saved. Before giving it a larger role, a small team should ask a narrower question: on one recurring, bounded workflow, does the verified result hold up while total team effort falls? That is an editorial recommendation for active experimentation, not a productivity gain demonstrated by the supplied evidence.

Start with a task that recurs and has a clear acceptance check. Record how the team handles it now, then keep the task, agent configuration and evaluation setup stable enough to compare repeat runs. GitHub’s [ReviewBench account](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/) describes versioning its dataset, judge and matcher so results can be compared under the same configuration. Stack Overflow’s [field guide](https://stackoverflow.blog/2026/10/08/production-grade-llms-and-agents-a-field-guide/) recommends comparing each release to a baseline. These are different settings, but together they suggest a useful discipline: preserve the conditions of the comparison, and treat changes in the task or evaluation as changes to the evidence. [03-c1]

Next, judge the artifact independently of the agent’s status report. For a code change, task-specific acceptance criteria and automated checks can sit alongside a record of human corrections, overrides and rework. A green run alone does not establish that the intended change happened; Stack Overflow’s [article on verification](https://stackoverflow.blog/2026/10/08/a-green-exit-code-is-not-evidence-that-the-work-happened/) argues that verification should not share the same failure mode as the work. GitHub’s guide to ReviewBench also illustrates why a single score can hide tradeoffs: review systems can favor broader issue coverage or fewer, more precise comments. A team should therefore inspect the kinds of defects found and missed, not just a pass/fail label. [03-c2]

Quality is only half the ledger. Count the human time spent setting up the task, waiting, reviewing, correcting and getting the change ready to deliver; record elapsed time too. In his account of building a newsletter feature, Simon Willison says voice interaction covered much of the initial work, but he switched to typing for a private-repository import and display changes, spending another half hour prompting before he was ready to deploy. That single practitioner account is not a comparison with a manual baseline. It does show why model runtime or coding time alone can miss work that returns to the person. [03-c3]

The same accounting should include operating cost and what happens when a limit is reached. In an [OpenAI-published Asana case study](https://openai.com/index/asana-browser-agent), Asana reports a 144-run study of one fixed browser task: collecting six fields for each of 32 books from a public demo catalog. It says an optimized GPT-6.1 Sol workflow averaged about four minutes and $0.47 in estimated model costs per run. Those figures describe that task and model spend, not a small team’s expected savings or full delivery cost. OpenAI has a commercial interest in the models and tools described. LegalOn’s [account of its cost controls](https://openai.com/index/legalon-halves-codex-costs), also published by OpenAI, says the company uses task-based model selection and limits; it also says a metric linking AI cost per feature to customer value is still being built. These examples support tracking cost per task and delivered change, with a spending ceiling and an explicit stop or fallback when it is reached. They do not validate one ceiling or routing policy for every team. Simon Willison’s [argument for hard budget caps](https://simonwillison.net/2026/Oct/3/default-hard-budget-caps/) makes the practical point that a warning can arrive after costs have already accrued. [03-c4] [03-c5]

If a trial grows to unattended or parallel runs, test the boundaries as part of the trial: whether state survives restarts, tools have only needed permissions, runs are isolated and time-limited, and failures are contained. In sampled passages from the Practical AI podcast, a guest describes storing state outside ephemeral agents and controlling MCP access through a gateway ([episode](https://share.transistor.fm/s/74934e48), [state persistence, 11:00](https://share.transistor.fm/s/74934e48?t=660), [MCP gateway, 24:21](https://share.transistor.fm/s/74934e48?t=1461)). Flywire’s [Agents in Orbit presentation](https://www.youtube.com/watch?v=rAUyRDOFyHU) describes read-only code review access, configurable time limits and isolated components ([read-only review, 11:48](https://www.youtube.com/watch?v=rAUyRDOFyHU&t=708), [timeouts, 9:27](https://www.youtube.com/watch?v=rAUyRDOFyHU&t=567)). Flywire also says online evaluations are not yet in place ([15:07](https://www.youtube.com/watch?v=rAUyRDOFyHU&t=907)). These are implementation accounts, not proof the safeguards work for a small team. The podcast excerpts were sampled from a publisher-provided transcript and have not been checked against the audio. [03-c6]

Expand the agent’s role when repeated runs show that acceptance quality holds, total human effort falls, cost stays within the team’s limit, and safety or failure signals remain acceptable. Narrow or stop the trial if quality slips, review and rework grow, access boundaries fail, or spending exceeds the limit. A longer or more costly run can still be worthwhile if the verified result justifies it; the ledger makes that judgment visible. The supplied evidence offers no controlled comparison showing that this process improves a small team’s productivity, and no single metric can settle every task.

Next edition: across repeated runs of one real team workflow, how often does verified quality hold while review time, rework and total cost change?
